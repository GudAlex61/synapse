# Отчёт функциональной проверки P2P-версии

Дата: 28 июля 2026.

## Что было проверено

### Модульные тесты

Команда:

```bash
node --no-warnings --experimental-strip-types --test tests/*.test.ts
```

Результат: **14 passed, 0 failed**.

Покрыты:

- Lamport-ревизии и защита от старых/дублирующихся команд;
- восстановление состояния из Postgres после потери Broadcast;
- разрешение одновременных команд;

- объединение истории и удаление дублей чата;
- генерация и валидация комнат, имён и URL;
- разбор STUN/TURN списка;
- строгая проверка и ограничение размера SDP payload.

### Браузерная симуляция владельца и зрителя

Создан 20-секундный MP4 с аудио и четырьмя визуально различимыми временными сегментами. Chromium декодировал файл у владельца, `captureStream()` создал две живые дорожки — `audio` и `video` — и этот MediaStream был подключён к отдельному read-only видеоплееру зрителя.

Пройдены сценарии:

1. старт воспроизведения — оба плеера показали красный первый сегмент;
2. пауза — hash кадра зрителя оставался неизменным в двух измерениях с интервалом 1 секунда;
3. перемотка на паузе к `5.2s` с одно-кадровым импульсом — зритель получил зелёный сегмент и поток снова остановился;
4. перемотка к `10.2s` — зритель получил синий сегмент;
5. возврат к `0` — зритель снова получил красный начальный сегмент;
6. в потоке отсутствовали browser errors.

Артефакты теста находятся в отдельном архиве `synapse-p2p-test-evidence.zip`:

- `capture-semantics.png` — два независимых плеера;
- `capture-results.json` — цвета, hash кадров, состояния и дорожки;
- `sample.mp4` — тестовый ролик;
- `unit-tests.txt` — полный TAP-вывод.

### WebRTC negotiation probe

В Chromium были успешно созданы offer и answer, оба SDP содержали секции `m=audio` и `m=video`, а обработчик `ontrack` получил две дорожки на стороне зрителя.

Полный RTP loopback в этой среде не установился: Chromium был запущен в административно ограниченной песочнице, HTTPS/localhost navigation блокировалась `ERR_BLOCKED_BY_ADMINISTRATOR`, а opaque-origin тест не получил ни одного ICE-кандидата. Состояния остались `new`, поэтому заявлять о полном сетевом E2E через ICE было бы нечестно. Машинный результат сохранён как `webrtc-probe.json` в архиве доказательств.

Это ограничение среды, но не доказательство работоспособности через произвольный NAT. После production-деплоя обязателен smoke-test на двух реальных сетях.

## Статическая проверка

- 27 TypeScript/TSX-файлов разобраны TypeScript Compiler API: **0 синтаксических ошибок**.
- Ядро без React/Next зависимостей прошло отдельный строгий `tsc --noEmit`.

## Проверенные архитектурные свойства

- байты видео не отправляются через Supabase Realtime или Postgres;
- локальный файл читается браузером поточно и не загружается целиком в оперативную память приложением;
- зритель не может породить обратный цикл `play/pause/seek` для P2P-источника;
- владелец является единственным контроллером локального P2P-потока;
- paused seek публикует один новый кадр и возвращается в паузу;
- offer/answer передаются как ограниченные маленькие JSON payload;
- сигналинг работает через RPC polling и не зависит от WebSocket `1006`;
- при ICE failure владелец создаёт ICE-restart offer, затем возможен полный повтор подключения;
- старое соединение закрывается и его remote tracks освобождаются;
- при обновлении зритель повторно объявляет готовность;
- File System Access handle сохраняется в IndexedDB там, где браузер это разрешает;
- пустая комната очищает state, chat, membership и signalling rows.

## Честные ограничения

1. Без TURN нельзя гарантировать прямое соединение для каждой пары сетей. STUN не заменяет relay при симметричном NAT/CGNAT или строгом firewall.
2. Владелец должен оставаться онлайн; при закрытии, sleep или агрессивном background suspension трансляция прекращается.
3. `captureStream()` имеет неодинаковую поддержку браузерами. Chrome/Edge являются целевым путём; Safari использует canvas/Web Audio fallback и требует отдельной production-проверки.
4. Качество WebRTC зависит не от размера файла, а от upload владельца, декодирования/кодирования устройства и текущей сети.
5. Проверка настоящего соединения через интернет возможна только после деплоя и запуска на двух реальных устройствах/сетях.
